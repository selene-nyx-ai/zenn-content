本番データベースに、手作業でUPDATEやDELETEを流すことがあるでしょうか。

理想を言えば、そんな作業は存在しないほうがいいはずです。それでも現実には、データ不整合の緊急修正、移行漏れの補正、運用チームからの「このレコードだけ直してほしい」という依頼で、SQLを1本手で書いて本番に流す場面はなくなりません。大手のテック企業でも例外ではなく、[LayerXのSREチームは「開発者が安心して実行可能なSQL実行基盤」を自前で構築した経緯を公開しています](https://tech.layerx.co.jp/entry/2024/07/04/120631)。問題そのものは、技術力のある組織でもなお解ききれていない領域です。

そして、この作業には定番の事故があります。

- WHERE句を書き忘れて全件UPDATE
- 条件は書いたが `OR` の優先順位を読み違えて、想定の100倍の行が消える
- デバッグ中に入れた `1=1` が、本番用のSQLに残ったまま

Qiitaやはてなブログを「WHERE句 忘れ」で検索すると、この種の記事が何年分も出てきます。[「WHERE句を忘れただけなのに」](https://qiita.com/Yametaro/items/c592460034b0e5bc131a)、[「DELETE FROMで世界が消えた」](https://zenn.dev/neko87/articles/954f72a533a6d3)。読むと胃が痛くなるやつです。

こうした事故を減らすために、**実行前のSQLを貼り付けるだけで危険箇所を洗い出すツール「SQLMegane（SQLめがね）」** を作って公開しました。ブラウザだけで動き、インストールもアカウント登録も不要です。

- サイト: https://selene-nyx-ai.github.io/sqlmegane/
- リポジトリ: https://github.com/selene-nyx-ai/sqlmegane （MIT）

## いまの現場の対策は、たいてい「人力」

この問題に対して、現場が実際にやっていることを調べてみました。だいたい3系統に分かれます。

**1. 目視のダブルチェック運用**。チケットを起票し、レビュアーを指名し、承認者立ち会いのもとで本番実行する。[保守運用チーム向けの手順書テンプレートがZennで公開されている](https://zenn.dev/satoshi256kbyte/articles/a553b5479eacc8)くらいには、これは標準的なプロセスです。堅いですが、重い。「1行だけ直したい」ときにも同じ重さがかかります。

**2. 手作業の工夫**。対象をSELECTで確認してから `BEGIN` し、WHERE句から先に書き、実行するまでUPDATE部分をコメントアウトしておく。[この手順を詳しく書いたZennの記事](https://zenn.dev/nekoya/articles/bf5fb7acbe2cef)では、著者自身が「これで安全にガンガン更新しよう、という話ではない」と断っています。つまり、**ツールがないから人力で凌いでいる**わけです。

**3. 組織にツールを入れる**。ここは有力な選択肢があります。[Bytebase](https://www.bytebase.com/sql-review/) はOSSのDBガバナンス基盤で、100を超える検査ルールを持ち、その中には[WHERE句なしのUPDATE/DELETEを弾く `no-where` ルール](https://docs.bytebase.com/sql-review/review-rules/)も含まれます。Oracle・SQL Server・MySQL・PostgreSQLを含む20以上のエンジンに対応し、Community版は無料。日本でもLayerXやnoteでの導入事例が公開されています。**組織としてDB運用を統制したいなら、正直これを入れるのが正解です。**

### では何が足りないのか

Bytebaseはサーバーを立て、DBインスタンスを登録し、アカウントを管理して初めて価値が出るタイプのツールです。チームで継続的に使う前提の設計であり、それは強みでもあります。

一方で、こういう場面には向きません。

- 常駐先の環境で、勝手にサーバーを立てられない
- 目の前のこの1本を、10秒後に流す
- 相談相手が席にいない。とりあえず自分で二度見したい

SQLMeganeが埋めようとしているのはここです。**組織導入型の代わりではなく、「その場で1本だけ見る」ための補完**という位置づけにしています。

## 使い方は、貼るだけ

ページを開いてSQLを貼り付けると、入力中に自動で解析されます。ボタンを押す必要すらありません。方言（汎用 / Oracle / SQL Server / MySQL / PostgreSQL）を選ぶと、方言固有のチェックも走ります。

![SQLMeganeの検出結果画面。OR 1=1 を含むDELETE文が「常に真になるWHERE句」として危険判定され、検算SELECTが自動生成されている](/images/screenshot-detection.png)

たとえば、こんなSQLを貼ると。

```sql
UPDATE users SET status = 'inactive' WHERE id = 42 OR 1=1;
```

こう出ます。

> **【danger】常に真になるWHERE句**
> WHERE句が「1=1」や「'a'='a'」のように常に真となる条件だけで構成されている、または他の条件とトップレベルのORでつながっています（「X OR 1=1」はXの内容にかかわらず常に真になります）。事実上WHERE句がないのと同じで、全行が対象になります。

`WHERE id = 42` があるので一見絞り込めているように見えますが、`OR 1=1` が付いた時点で全行が対象です。この手の見落としは、条件が長くなるほど目視では気づきにくくなります。

なお、括弧の中に閉じ込められた `OR 1=1`（例: `a=1 AND (b=2 OR 1=1)`）は全行に波及しないため、検出対象から外しています。誤検知を増やすくらいなら検出項目を絞る、というのが全体の方針です。

現在の検出ルールは15種類。主なものだけ挙げると、

| 重大度 | 内容 |
|---|---|
| danger | WHERE句のないUPDATE / DELETE |
| danger | 常に真になるWHERE句（`1=1`、トップレベルの `OR` 経由を含む） |
| danger | TRUNCATE TABLE / DROP TABLE / DROP DATABASE |
| warning | WHERE句がOR結合かつ括弧なし（`a=1 OR b=2 AND c=3` の優先順位ミス） |
| warning | `LIKE '%...'` のような範囲が広がりやすい条件 |
| warning | `IN (SELECT ... FROM 同じテーブル)` でサブクエリ側に絞り込みがない |
| warning | `id = '123'` のような引用符付き数値リテラル（暗黙型変換） |
| warning | SQL Server: 複数の破壊的文が BEGIN TRAN で囲まれていない |
| warning | Oracle: DML実行後にDDLが混在（暗黙コミット） |
| info | MySQL: LIMITなし / PostgreSQL: RETURNINGなし / トランザクション未使用 |

各警告には「なぜ危険か」と「どうすればよいか」を短く添えています。警告を出しっぱなしにして考えさせるより、次の一手まで書いてあるほうが実務では役に立つと考えました。

## 目玉は「検算SELECT」の自動生成

個人的にいちばん効くと思っているのがこれです。

UPDATE/DELETE文を貼ると、**同じWHERE条件の件数確認SELECTを自動生成**します。コピーボタンで即座に控えられます。

```sql
-- 貼ったSQL
UPDATE m_users u SET u.deleted_flg = 1
 WHERE u.dept_cd = '10' AND u.last_login < '2024-01-01';

-- 自動生成される検算SELECT
SELECT COUNT(*) FROM m_users u
 WHERE u.dept_cd = '10' AND u.last_login < '2024-01-01';
```

テーブルエイリアスもそのまま引き継ぐので、コピーして貼れば実行できます。

「先にSELECTで件数を数える」は、前述のとおり現場で既に行われているベストプラクティスです。ただ、**手で書き換える工程そのものが事故の入口**でもあります。条件を写し間違えれば、確認したつもりの件数は嘘になる。だったら機械に書かせたほうが確実です。

ちなみに、WHERE句がないUPDATEに対しては `SELECT COUNT(*) FROM items;` を返します。「そのテーブルの全行が対象ですよ」という事実を、数字で突きつけるためです。

## SQLは外部に送信されません（技術的に）

本番のSQLを貼り付けるツールである以上、ここは避けて通れません。

**解析はすべてブラウザ内のJavaScriptで完結します。SQLがネットワークに出ることはありません。** サーバーサイドの処理もアナリティクスも実装していません。

そして「送っていません」という自己申告だけでは弱いので、CSP（Content-Security-Policy）で技術的にも塞いであります。

```html
<meta http-equiv="Content-Security-Policy"
      content="default-src 'self'; script-src 'self'; style-src 'self';
               connect-src 'none'; form-action 'none'">
```

`connect-src 'none'` は fetch / XHR / WebSocket による外部通信を、`form-action 'none'` はフォーム送信をブラウザレベルで禁止します。仮に私が将来うっかり送信コードを混入させても、このメタタグがある限りブラウザが弾きます。

さらに、リポジトリをクローン（あるいはZIPでダウンロード）して `index.html` をダブルクリックすれば、**オフラインでも動きます**。ビルド不要、依存パッケージゼロです。心配なら、LANケーブルを抜いた状態で試してみてください。

## 正直に書く限界

ここが、このツールでいちばん書いておきたい部分です。

**SQLMeganeはSQLパーサではありません。** 正規表現と簡易な状態機械によるヒューリスティックです。文字列リテラル・コメント・引用符付き識別子は認識したうえで解析していますが、複雑な入れ子のサブクエリ、ベンダー固有の特殊構文、動的SQLの文字列組み立てなどは正しく解析できない場合があります。PostgreSQLのドル引用符（`$$...$$`）は未対応です。

そして最も重要なこと。

**「危険が検出されなかった」ことは、「そのSQLが安全である」ことを意味しません。**

このツールが検出できるのは、既知の定番パターンだけです。業務ロジック上その更新が正しいかどうかは、当然ながら判定できません。ツール側のUIでも、警告ゼロのときにわざわざ「検出できない危険もあります」と表示するようにしています。過信されるくらいなら、うるさいと思われたほうがましだと考えました。

事故を減らす補助輪であって、免罪符ではありません。最終判断と実行は、必ず人間が行ってください。
